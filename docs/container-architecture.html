01 · Architecture · Build once, start fresh containers

Two phases with different responsibilities

The Dockerfile creates a reusable image with Git, Python 3.12, pip, a virtual environment, and an entrypoint script. Starting a container invokes that script, which performs the clone and installation before launching the application.

What Docker provides

Docker Desktop hosts the Linux engine on this Windows machine. The engine creates the container's process, network, and filesystem environment from the image. The Dockerfile explicitly chooses Python and installs Git and certificate authorities with Debian's apt package manager.

The image build obtains the Python base image from Docker Hub and OS packages from Debian repositories. The diagram groups those downloads into the builder box.

What our script provides

run-repo.sh reads REPO_URL, optionally selects a branch or tag using REPO_REF, clones into repo, changes directory, prints the commit, runs pip, and executes the command. The Dockerfile supplies sample as the default command.

set -eu stops on a failed clone or install. exec "$@" replaces the shell with the requested program, so its output and exit status become the container's output and exit status.

Implementation references are Dockerfile and run-repo.sh. Container execution model described in Docker's container documentation.

02 · Sequence · What pip does during startup

The repository declares what to install

The dot in python -m pip install --no-cache-dir . means “install the project in the current directory.” In this checkout, pyproject.toml supplies the build backend, runtime requirements, Python compatibility constraint, and executable entry point.

[build-system]
requires = ["setuptools"]
build-backend = "setuptools.build_meta"

[project]
name = "sampleproject"
version = "4.0.0"
requires-python = ">=3.9"
dependencies = ["peppercorn"]

[project.scripts]
sample = "sample:main"

Three declarations, three purposes

Build requirements supply tools needed to turn source into an installable wheel. Here that tool is setuptools.

Runtime dependencies become installed libraries. Here pip selects peppercorn 0.6.

Scripts describe generated commands. sample = "sample:main" asks the installer to create a launcher that imports main from the sample module and calls it.

How the dependency list is discovered

Pip loads the build-system declaration and runs the backend's metadata hooks. Setuptools reads the project's metadata and emits dependency requirements such as Requires-Dist: peppercorn. Pip follows each requirement's metadata recursively, checks Python and platform compatibility, and chooses a consistent set of versions. Conflicts can cause backtracking or an installation error.

The current manifest leaves peppercorn's version unconstrained. The inspected run chose version 0.6. Peppercorn has no additional mandatory runtime dependencies in that inspected metadata. Optional extras are activated explicitly, for example pip install '.[test]' for this repo's test extra.

Pip dependency resolution · Build-system interface

How bytes reach the container

With pip's defaults, package discovery uses https://pypi.org/simple. Pip requests metadata and distribution files over HTTPS, typically fetching files from files.pythonhosted.org. An index URL can also be configured for a private package registry. Docker's outbound networking carries those requests.

A wheel (.whl) is an installable archive. Pip downloaded peppercorn's wheel and built a sampleproject wheel from the local checkout. Installation places package files and metadata in the virtual environment and creates the command launcher.

Pip install options and stages

Diagram scope. The PyPI actor combines index discovery and file hosting. Each “resolve + get” arrow summarizes multiple requests. Temporary build setup and cleanup happen inside pip. The observed log follows this high-level order, while individual backend calls and downloads can vary with packaging tools and cached state.

03 · Nested filesystem · Where the code lives

Source checkout and installed packages have separate paths

The image sets PATH=/home/runner/venv/bin:…. This makes python resolve to the virtual environment's interpreter and makes the generated sample command discoverable. Python uses its import search path to find the installed package modules.

What the command actually executes

The generated /home/runner/venv/bin/sample launcher begins with #!/home/runner/venv/bin/python. It imports main from sample and calls it. In the inspected run, sample.__file__ resolved to the installed copy under site-packages.

The distribution name is sampleproject, its importable module is sample, and its command is also sample. These names come from packaging configuration. The demo's main function prints a message. A separate inspection confirmed that peppercorn imports successfully.

How long the files last

The image contains the starting filesystem. Git's checkout and pip's installation add files to that container's writable layer. Removing the container removes those writes. With docker run --rm, removal happens automatically when the main process exits.

The image remains available for the next run. Every new container repeats the clone and install. A named volume or bind mount would give selected paths a separate lifetime. This lab currently uses the container layer for its runtime files.

Engineering discussion

A concise explanation you can give

“We build a reusable Linux image with Python, Git, and a non-root runtime user. On startup, the entrypoint clones a selected Python repository and runs pip against the checkout. Pip obtains project metadata through the declared build backend, resolves the dependency graph against a package index, builds the local project into a wheel, and installs the application and dependencies into a virtual environment. The entrypoint then replaces itself with the application's command. The checkout and installed packages live in the container's writable layer, so this trial recreates them on each run.”

How does it know about every dependency?

Package authors declare requirements in package metadata. Pip follows those declarations transitively. Correct installation depends on complete metadata. A missing declaration can surface as an import error or missing library at runtime. OS packages and external services also require explicit setup.

What makes this specific to Python?

The image chooses Python 3.12 and the script chooses pip install .. Another repository needs a compatible runtime, supported installation command, and correct start command. A requirements-file project needs an explicit pip install -r requirements.txt step. A Node project typically uses its own manifest, lockfile, Node runtime, and package manager.

Will two runs always install the same versions?

The current default follows the remote repository's default branch and has unpinned dependency versions. The Python image tag is also mutable between builds. Reproducibility requires controlling the source revision, base image digest, build tools, and dependency versions or hashes. The current REPO_REF implementation supports a branch or tag through git clone --branch. Exact commit checkout would require an explicit fetch and checkout step.

What changes for deployment?

This trial places clone and install work at startup, making network access and package availability part of each launch. A deployable application image can instead contain the selected source and installed dependencies at build time. That moves resolution failures into the build and makes startup faster. Private repositories also need an explicit credential mechanism, and applications may require configuration, ports, persistent storage, or supporting services.

What does successful execution prove?

We observed a successful Git checkout, downloaded and installed peppercorn 0.6, built and installed sampleproject 4.0.0, imported both modules, and ran the sample command with exit code 0. This verifies the clone → install → execute path for this Python packaging example. Compatibility with another repo depends on that repo's own runtime contract.

Hands-on verification

See the same evidence yourself

From PowerShell, run the following command to clone, install, and open a shell in the checkout.

docker run --rm -it repo-lab sh

Inside that Linux shell, inspect the declarations, interpreter, installed metadata, import paths, and generated launcher.

pwd
git rev-parse HEAD
cat pyproject.toml
command -v python
python -m pip show sampleproject peppercorn
python -m pip check
python -c 'import sample, peppercorn; print(sample.__file__); print(peppercorn.__file__)'
cat /home/runner/venv/bin/sample
sample
exit

pip show reports package versions and installation locations. pip check checks declared dependency compatibility. __file__ shows which file Python actually imported. Exiting removes this trial container because it was started with --rm.
